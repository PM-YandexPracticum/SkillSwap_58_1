# Мок-сервер SkillSwap

## инструкция по серверу

- Сначала из корня проекта установи зависимости сайта и сервера: `npm i`, затем `npm --prefix server i`.
- Из корня проекта запусти сервер: `npm --prefix server run dev`.
- Во втором терминале из корня проекта запусти сайт: `npm run dev`.
- Данные пишутся в JSON-файлы в `server/data/`, фото навыков — в `server/data/uploads/skills/<skillId>/`, аватарки — в `server/data/uploads/avatars/<userId>/`.
- Для сброса останови сервер (`Ctrl+C`), выполни `npm --prefix server run reset` и запусти сервер снова. Фото удалятся, данные вернутся к исходным мокам.
- У каждого свой локальный сервер: данные и фото хранятся только на твоём компьютере.
- При первом старте \ ресете моки на сервер подгружаются из `/public/db` поэтому эти моки не удаляй
```bash
npm --prefix server ci
npm --prefix server run dev       # http://localhost:4000/api
npm --prefix server run typecheck
npm --prefix server test
npm --prefix server run reset     # удалить базу и загруженные изображения
```

### Запросы с фронта

Обращайся по относительному `/api`: Vite перенаправит запросы на `http://localhost:4000`.

```ts
fetch('/api/skills')
fetch('/api/users')
fetch('/api/auth/me')
```

В Axios укажи `baseURL: '/api'`. Напрямую API доступен по `http://localhost:4000/api`.

## Вход

`POST /api/auth/login`, `Content-Type: application/json`:

```json
{ "email": "anna.smirnova@example.com", "password": "SkillSwapMock2025!" }
```

Почта обрезается по краям и приводится к нижнему регистру. Пароль передаётся
без преобразований. Ответ `200`: `{ id, name, email, token }`.
Некорректное тело — `400`, неверные учётные данные — `401` с одинаковым
сообщением для неизвестной почты и неверного пароля.

## Регистрация

`POST /api/auth/register`, `multipart/form-data`:

- `data`: текстовое поле с JSON формы из примера ниже;
- `images`: необязательное поле, до 5 фотографий навыка, каждый файл отдельной частью с тем же именем;
- `avatar`: необязательная фотография пользователя, один файл.

Для регистрации без фото передайте только `data`. Аватар можно передать вместе
с фотографиями навыка или без них, в том же запросе регистрации.

```json
{
  "email": "new@example.com",
  "password": "SkillSwapMock2025!",
  "name": "Анна",
  "birthDate": "1995-02-08T00:00:00.000Z",
  "gender": "female",
  "city": "Москва",
  "wantsToLearn": ["english", "acting"],
  "canTeach": {
    "title": "Уроки рисования",
    "category": "art",
    "subCategory": "illustration",
    "description": "Научу рисовать акварелью"
  }
}
```

Все поля JSON `data` обязательны. Имя — минимум 2 символа, пароль — минимум 8,
название навыка — 3–50, описание — 1–500. Текстовые поля обрезаются по краям,
кроме пароля. Дата рождения — канонический ISO UTC из `Date.toISOString()`,
существующая и не в будущем; минимального возраста нет. Пол — `female | male`,
город — только из `CITIES`.

`wantsToLearn` — непустой массив строк типа `SubCategoryId[]`, без повторений.
ID подкатегорий берутся из `SKILL_CATEGORIES`; категории отдельно не передаются.
Объект вместо массива, неизвестные ID и значения других типов отклоняются с `400`.
Подкатегория преподаваемого навыка должна принадлежать его категории.

Изображения — JPEG, PNG или WebP, до 2 МБ каждое. Сервер проверяет MIME-тип и
сигнатуру. Порядок файлов сохраняется. В браузере запрос формируется так:

```ts
const form = new FormData()
form.append('data', JSON.stringify(data))
const files = images ?? [] // images: File[] | null | undefined
files.forEach((file) => form.append('images', file))
if (avatar) form.append('avatar', avatar) // avatar: File | null
await fetch('/api/auth/register', { method: 'POST', body: form })
```

Если форма хранит один файл (`teachImage: File | null`), список файлов собирается как
`const images = teachImage ? [teachImage] : []`. При отсутствии фото поле `images`
в `FormData` не добавляется. Не передавайте вместо файлов `null`, строку `'null'`,
`JSON.stringify([])` или пустую строку: это текстовые части multipart, сервер вернёт `400`.
В состоянии формы для списка файлов рекомендуется `File[]` с начальным значением `[]`.

`Content-Type` вручную не задаётся: браузер добавляет multipart boundary.

Регистрация создаёт пользователя и навык `type: 'teach'`, связывает их через
`authorId` и `canTeach.id`. Ответ `201`: `{ id, name, email, token }`;
при загрузке аватара ответ также содержит `avatarUrl`.
Ошибка формы или файлов — `400`, занятая почта — `409`.
Все ошибки возвращаются как `{ message: string }`.

Файлы сохраняются в `server/data/uploads/skills/<skillId>/<uuid>.<extension>`.
`GET /api/skills/:id` возвращает только `imageUrls: string[]` для изображений навыка.
Выбор изображения для обложки выполняет фронтенд. Ссылки начинаются с
`/api/uploads/skills/` и доступны как статика, в том числе через Vite-прокси.
Без загруженных изображений навык сохраняется с `imageUrls: []`.
Аватар сохраняется в `server/data/uploads/avatars/<userId>/<uuid>.<extension>`,
как при `PATCH /api/auth/me`; его URL `/api/uploads/avatars/...` записывается
в `User.avatarUrl` и доступен через профиль и публичные списки пользователей.
Проверки MIME-типа, сигнатуры и лимит 2 МБ совпадают с PATCH. Без аватара
`avatarUrl` равен `null`. При последующей замене через PATCH прежний файл удаляется.
При ошибке сохранения регистрации файлы удаляются, запись навыка откатывается.
Две JSON-базы не обеспечивают транзакции при аварийном завершении процесса.

## Редактирование профиля

`PATCH /api/auth/me` обновляет только пользователя из токена
`Authorization: Bearer <token>`. Ответ `200` — полный обновлённый профиль без пароля.
Неуказанные поля сохраняются. Разрешены:

| Поле | Значение |
| --- | --- |
| `email` | Корректная уникальная почта; пробелы по краям удаляются, регистр понижается |
| `name` | Имя от 2 символов после удаления пробелов по краям |
| `birthDate` | Существующая дата ISO UTC из `Date.toISOString()`, не в будущем |
| `gender` | `female` или `male` |
| `city` | Название города из `CITIES` |
| `bio` | Строка до 500 символов; пустая строка очищает описание |

Для изменения полей без файла отправляйте JSON с `Content-Type: application/json`:

```json
{ "name": "Мария", "bio": "Люблю учиться новому" }
```

С аватаркой отправляйте `multipart/form-data`: `data` — JSON с изменяемыми полями,
`avatar` — один файл JPEG, PNG или WebP до 2 МБ. Можно передать только файл,
без `data`, или только `data`. `Content-Type` браузер выставляет сам.

```ts
const form = new FormData()
form.append('data', JSON.stringify({ name: 'Мария', city: 'Москва' }))
form.append('avatar', avatarFile)
const response = await fetch('/api/auth/me', {
  method: 'PATCH',
  headers: { Authorization: `Bearer ${token}` },
  body: form,
})
const updatedUser = await response.json()
```

Новая аватарка получает уникальный URL `/api/uploads/avatars/<userId>/<uuid>.<ext>`;
используйте `avatarUrl` из ответа, чтобы браузер не показывал старый файл из кеша.
Предыдущая загруженная аватарка удаляется после сохранения профиля. При ошибке
сохранения новый файл удаляется, старый профиль и аватарка остаются. Статические
аватарки из `/db/avatars/` и внешние URL не удаляются. Без нового файла аватарка
сохраняется. При сбое удаления старого файла обновление остаётся успешным,
ошибка очистки записывается в журнал сервера.

Ошибки: `400` — пустой запрос, неизвестные поля, некорректные данные или файл;
`401` — нет действительного токена; `409` — почта другого пользователя;
`500` — ошибка сохранения. Формат ошибок — `{ message: string }`.
Поля `id`, `password`, `avatarUrl`, `likes`, `canTeach`, `wantsToLearn`, `createdAt`
через эту ручку не изменяются и отклоняются с `400`. Смена пароля — отдельное
действие по ссылке в форме; эта ручка его не реализует.

## Профиль и списки

`GET /api/auth/me` принимает `Authorization: Bearer <token>` и возвращает
полный профиль без `password` и `login`, с массивом `wantsToLearn`.
Токены и пароли здесь предназначены для локального мока.

Существующие ручки `/api/users`, `/api/users/:id`, `/api/skills`, `/api/skills/:id`
сохраняются. Пагинация возвращает `{ items, page, limit, total, hasMore }`.
Навыки поддерживают фильтры `category`, `subCategory`, `type`, `q`;
пользователи — сортировки `new`, `popular`, `random`.

`GET /api/users` также принимает необязательные фильтры:

- `gender`: `female` или `male`; без параметра — любой пол.
- `city`: точное название из `CITIES`, например `Москва`.
- `city[]`: несколько городов через повторение ключа, например
  `city[]=Москва&city[]=Казань`. Достаточно совпадения одного города; дубликаты
  не дублируют пользователей. Пустые и неизвестные города возвращают `400`.
  Если переданы и `city`, и `city[]`, применяются оба ограничения через И.
- `type`: желание посетителя — `learn` («хочу научиться», поиск в
  `canTeach.subCategory`), `teach` («могу научить», поиск в `wantsToLearn`),
  `all` (по умолчанию, поиск в обоих полях).
- `subCategoryId[]`: ID из `SKILL_CATEGORIES`. Для массива повторяй ключ:
  `?subCategoryId[]=english&subCategoryId[]=german`. Достаточно совпадения
  хотя бы одного ID; повторяющиеся ID не дублируют пользователей.
- `ids[]`: ID пользователей, например `?ids[]=user-01&ids[]=user-02`.
  Повторяющиеся ID учитываются один раз, неизвестные пропускаются. Без параметра
  ограничений по ID нет; `ids[]=` и значения из одних пробелов возвращают `400`.
  Для избранного передавайте ID из существующего `likes` профиля `/api/auth/me`.
  Каталог остаётся публичным: фильтр выбирает переданные ID, независимо от лайков.
- `name`: подстрока названия, поле поиска выбирает `type`: `learn` — название
  навыка по `canTeach.id`; `teach` — названия подкатегорий из `wantsToLearn`
  по справочнику `SKILL_CATEGORIES`; `all` (по умолчанию) — оба поля через ИЛИ.
  Регистр не учитывается, пробелы по краям удаляются. Пустое,
  состоящее из пробелов или отсутствующее значение не ограничивает список.
  Например, `type=learn&name=БАРАБАН` найдёт навык «Игра на барабанах»,
  а `type=teach&name=АНГЛ` — желающих изучать «Английский».
  Имя пользователя, теги, описание и ID подкатегорий не участвуют в поиске;
  склонения слов не приводятся к общей форме.

Фильтры объединяются через И и применяются до сортировки и пагинации;
`total` и `hasMore` относятся к отфильтрованному списку. Без `subCategoryId[]`
и непустого `name` ограничения по навыкам нет, в том числе при переданном `type`.
Недопустимые значения, пустые значения фильтров (кроме `name`), повторение
одиночного параметра (`gender`, `city`, `type`, `name`) возвращают `400` с `{ message }`.

```text
GET /api/users?gender=female&type=learn&subCategoryId[]=english&subCategoryId[]=german&city=Москва
GET /api/users?ids[]=user-01&ids[]=user-02&name=БАРАБАН&page=1&limit=12
GET /api/users?type=teach&name=АНГЛ&page=1&limit=12
GET /api/users?city[]=Москва&city[]=Казань&sort=new&page=1&limit=9
```

`likes` — ID пользователей, которым пользователь поставил лайк. Для сортировки
`popular` сервер считает входящие лайки; счётчик `likesReceived` остаётся внутри
сервера и не передаётся в ответах `/api/users`, `/api/users/:id` и `/api/auth/me`.

## Лайки пользователей

`PUT /api/auth/me/likes/:targetUserId` добавляет ID получателя в существующий
массив `likes` владельца токена. `DELETE /api/auth/me/likes/:targetUserId` удаляет
его оттуда. Оба запроса требуют `Authorization: Bearer <token>`, тело не требуется.
Остальные поля профиля и лайки других пользователей сохраняются.

| Запрос | Ответ |
| --- | --- |
| `PUT`, лайка ещё нет | `201`, пустое тело |
| `PUT`, лайк уже есть | `204`, пустое тело |
| `DELETE`, в том числе повторный | `204`, пустое тело |

Нет действительного токена — `401`; получатель не найден — `404`; ошибка записи
базы — `500`. Ошибки имеют формат `{ message: string }`. Авторизация проверяется
до поиска получателя. Повторные запросы не создают дубликатов и не меняют
популярность повторно.

Изменения сохраняются в `server/data/users.json` и переживают перезапуск.
Профиль в памяти и внутренний счётчик входящих лайков обновляются только после
успешной записи; при ошибке сохранения прежнее состояние остаётся. Сортировка
`popular` учитывает изменение сразу. `PATCH /api/auth/me` по-прежнему не принимает
поле `likes`: для изменения используются только операции выше.

Для получения избранных пользователей используйте существующий `/api/users`
с повторяющимся параметром `ids[]` из `likes`. Если избранных нет, запрос без
`ids[]` вернёт обычный каталог; пустой массив в query не передаётся.

## Заявки на обмен

Пользователь предлагает обмен со страницы чужого навыка, автор навыка принимает
или отклоняет его. Все ручки требуют `Authorization: Bearer <token>`; без
действительного токена — `401`.

| Запрос | Кто | Тело | Ответ |
| --- | --- | --- | --- |
| `POST /api/swap-requests` | любой пользователь | `{ "skillId": "skill-07" }` | `201`, заявка |
| `GET /api/swap-requests` | участник | — | `200`, `{ items, page, limit, total, hasMore }` |
| `PATCH /api/swap-requests/:id` | получатель | `{ "status": "accepted" }` или `"rejected"` | `200`, заявка |
| `DELETE /api/swap-requests/:id` | инициатор | — | `204`, пустое тело |

Инициатор берётся из токена, получатель — автор навыка (`skill.authorId`):
клиент передаёт только `skillId`. Обмениваются навыки `canTeach` обоих
пользователей, тип навыка (`teach` или `learn`) не проверяется.

Каждая заявка в ответах — `SwapRequest` (`id, skillId, fromUserId, toUserId,
status, createdAt, updatedAt`) и связанные данные:

- `fromUser`, `toUser` — публичные профили, как в `/api/users`;
- `skill` — навык получателя, на который предложен обмен;
- `offeredSkill` — навык инициатора (`fromUser.canTeach`), который он предлагает взамен.

Тип ответа — `SwapRequestDetails` в `src/shared/types/index.ts`. Статусы: `pending`,
`accepted`, `rejected`; `inProgress` и `done` из общего типа сервер не использует.

### Жизненный цикл

```text
POST ─► pending ─PATCH accepted (получатель)─► accepted   итог, удалить нельзя
          │ └───PATCH rejected (получатель)─► rejected ─DELETE (инициатор)─► удалена
          └──DELETE (инициатор отзывает)─► удалена
```

| Статус | Инициатор | Получатель |
| --- | --- | --- |
| `pending` | «Отправлен», может отозвать | «Предложен вам», может принять или отклонить |
| `accepted` | «Подтверждён» | «Подтверждён» |
| `rejected` | «Отклонён», может удалить | заявки нет в списке |

### Список

`GET /api/swap-requests` возвращает заявки владельца токена, новые первыми.
Пагинация как у остальных списков: `page`, `limit` (по умолчанию 10, максимум 100).

- `role`: `incoming` — входящие, `outgoing` — исходящие, `all` (по умолчанию) — обе.
- `status`: `pending`, `accepted` или `rejected`; без параметра — любой.

Отклонённые заявки получатель не видит. Неизвестные или повторённые значения
`role` и `status` возвращают `400`.

```text
GET /api/swap-requests?role=incoming&status=pending   входящие предложения
GET /api/swap-requests?role=outgoing                  отправленные, в том числе отклонённые
GET /api/swap-requests?status=accepted                подтверждённые обмены
GET /api/swap-requests?role=incoming&status=pending&limit=1   total — счётчик новых
```

### Правила и ошибки

| Код | Когда |
| --- | --- |
| `400` | лишние или неверные поля; навык `skillId` не найден; свой навык; неверный `role` или `status` |
| `401` | нет действительного токена |
| `403` | инициатор отвечает на свою заявку; получатель удаляет заявку |
| `409` | повторное предложение на тот же навык; встречная заявка `pending` или `accepted` от получателя; ответ на уже обработанную заявку; ответ на отозванную заявку («Заявка отозвана»: её нет или пользователь в ней не участвует); удаление подтверждённого обмена |
| `500` | ошибка записи базы |

- Отклонённая заявка остаётся у инициатора: чтобы предложить обмен снова, её нужно удалить.
- Встречная заявка описывает тот же обмен, поэтому получатель не может предложить
  его в ответ, пока заявка инициатора ожидает ответа или подтверждена. После
  отклонения встречное предложение разрешено.
- Повторный `PATCH` с текущим статусом возвращает `200` без изменений. Повторный
  `DELETE`, как и удаление чужой или несуществующей заявки, возвращает `204` и
  ничего не меняет. Это защищает от двойного клика и не вызывает переход на страницу 404.
- Ненайденный `skillId` возвращает `400`, а `PATCH` по отозванной заявке — `409`,
  а не `404`: `baseApi` на фронте по `404` уводит на страницу «не найдено».

Заявки хранятся в `server/data/swap-requests.json`. Если файла нет, при старте он
создаётся из `public/db/swap-requests.json`; `reset` для этого не нужен. В сидах —
по одной заявке на каждое состояние для демо-входа Анны (`user-01`): входящая от
Марии, исходящие к Ольге (ожидает), Софии (подтверждена) и Алине (отклонена).
Изменения сохраняются только после успешной записи файла.

## Задержка

Имитация: по умолчанию задержка 1000 мс; `?delay=1500` меняет её в пределах
1000–5000 мс. Неизвестные параметры игнорируются. Раздача изображений выполняется
без искусственной задержки.

## Postman

Коллекция и исходник документации: [skillswap.postman_collection.json](postman/skillswap.postman_collection.json).
Она содержит папку **«Справочник API»** с основными запросами и сохранёнными
примерами ответов: успешные ответы и ошибки `400`, `401`, `404`, `409`.
Примеры сняты с работающего сервера на отдельной временной базе из сидов;
ID, почта и время создания при повторной регистрации будут другими.

### Открыть документацию и отправить запросы

1. В Postman Desktop нажмите **Import** и выберите файл коллекции выше.
2. Для просмотра описаний откройте коллекцию → **Overview → View complete documentation**.
   Примеры ответов также доступны в **Examples** под соответствующим запросом.
   Для чтения примеров запускать сервер не нужно.
3. Для отправки запросов запустите из корня проекта `npm --prefix server run dev`.
   Переменная коллекции `baseUrl` уже равна `http://localhost:4000/api`.
   Для проверки Vite-прокси замените её на `http://localhost:5173/api` и запустите `npm run dev`.
4. В настройках Postman **Settings → General → Working directory** выберите
   корень репозитория. Файлы регистрации и аватарок лежат в `server/postman/fixtures/`.
5. Начните со **«Справочник API → Вход»**, затем **«Мой профиль»**:
   токен сохранится в `authToken` автоматически. Списки и получение по ID
   доступны без авторизации. Запрос **«Регистрация»** создаёт пользователя,
   навык и пять изображений; уникальная почта генерируется перед отправкой.
6. **«Изменить профиль — поля»** отправляет частичное обновление в JSON,
   **«Изменить профиль — аватарка»** — `multipart/form-data` с `data` и `avatar`.
   Используется `authToken` из входа. Эти запросы меняют профиль владельца токена.
   Примеры ошибок `400`, `401`, `409` находятся в Examples; пример неверной аватарки
   содержит текстовый файл с поддельным MIME изображения.

В справочнике описаны авторизация, обязательные поля, ограничения файлов,
пагинация, фильтрация, сортировка и коды ошибок. Пример ошибки содержит
тот запрос, который её вызвал: например, неверный пароль или занятая почта.
Учётные данные и токены в примерах относятся только к учебному моку.

### Полный прогон проверок

Следующие папки — сценарии: **«Навыки»**, **«Пользователи»**,
**«Авторизация»**, **«Редактирование профиля»**, **«Лайки и поиск»**,
**«Имитация и хвост»**. Запросы
передают переменные следующим запросам. Запускайте папки целиком по порядку.

```bash
postman collection run server/postman/skillswap.postman_collection.json \
  --working-dir . --no-report-events
```

Папка **«Лайки и поиск»** запускается самостоятельно: выполняет вход, выбирает
пользователя, которого ещё нет в `likes`, проверяет постановку, повторные запросы,
поиск по названию, фильтр `ids[]`, ошибки и CORS, затем снимает тестовый лайк.
При успешном завершении исходный массив `likes` восстановлен. Если прогон
прерван после постановки лайка, он может остаться в локальной базе.

```bash
postman collection run server/postman/skillswap.postman_collection.json \
  -i 'Лайки и поиск' --working-dir . --no-report-events
```

Папка **«Редактирование профиля»** содержит 17 последовательных запросов.
Она использует `newToken`/`newUserId` после регистрации: меняет почту и поля,
проверяет вход с новым адресом и отказ со старым, защищённые поля и ошибки,
заменяет аватарку, проверяет удаление старого файла и сохранность навыка.
Для запуска только этого сценария сначала выполните папку **«Авторизация»**:

```bash
postman collection run server/postman/skillswap.postman_collection.json \
  -i 'Авторизация' -i 'Редактирование профиля' \
  --working-dir . --no-report-events
```

Прогон создаёт тестового пользователя, навык и изображения, меняет его профиль
и почту. Используйте локальную или временную базу. Повторный запуск
поддерживается: почта генерируется заново, последняя страница навыков вычисляется
по текущему количеству. При необходимости очистите данные командой `reset`.

### Как поддерживать документацию

- Этот README описывает запуск и общие правила; коллекция — отдельные запросы,
  параметры, тела и примеры ответов. Ссылки на оба файла находятся в корневом README.
- При изменении API обновите описания и Examples в той же задаче.
- После редактирования в Postman экспортируйте коллекцию в формате v2.1
  обратно в `server/postman/skillswap.postman_collection.json` для проверки через PR.
- Перед экспортом очистите значения переменных прогона (`authToken`, `newToken`,
  `newEmail`, `newUserId`, `newSkillId` и других вычисляемых переменных).
  Оставьте `baseUrl` и демонстрационные `demoEmail`/`demoPassword` из сидов.
- Изменение файла в Git не обновляет ранее импортированную копию в Postman:
  её нужно обновить импортом. Публикация страницы — отдельный шаг;
  импорт коллекции её не публикует и не размещает локальный сервер в интернете.
- При подключении редактирования на фронтенде обновляйте сохранённого пользователя
  и кеш запросов из ответа PATCH: старые имя, почта и `avatarUrl` сами не обновятся.
  Токен после смены почты остаётся прежним; вход выполняется уже с новой почтой.
